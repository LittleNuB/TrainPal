# 0050：代码审查与运行镜像发布分离

状态：已接受（2026-09-11，用户确认继续处理 Issue #4 的发布边界）

## 背景

当前用户允许向个人仓库推送代码、创建 Issue 和 Draft PR，但尚未允许合并、部署或恢复云端入口。历史 Competition image 工作流在 main / competition/web-mvp push 时会尝试向队友名下的 GHCR 地址发布镜像，这与当前个人仓库和暂停发布边界不符。

## 决策

- 常规 CI 保持原有 pull_request、指定分支 push 和 workflow_call 触发方式，仅执行质量验证。
- competition-image 工作流只保留显式 workflow_dispatch，名称明确为手动镜像验证；不因代码推送或 PR 自动启动镜像构建。
- 手动镜像验证仅在临时 runner 内构建、加载和审计镜像，继续保留 CI 前置门、镜像层审计、容器 smoke、Caddy 和 Compose 配置校验。
- 移除 packages 写权限、注册表登录、发布目标、发布元数据与 docker push 步骤，不替换成另一未经确认的注册表。
- 本次不调用该手动工作流，不操作任何云资源或已有镜像。工作流通过也不等于公网可用、真实 Provider 验证或部署成功。
- 恢复镜像发布必须另行获得明确授权，核对个人仓库拥有的发布目标、最小权限、质量门禁及回滚，并通过单独 PR 审查；不能把普通 Ready/Merge 当成部署授权。

## 验证与局限

配置回归测试检查触发条件、写权限/发布路径的缺失，以及已有本地审计步骤的保留。它是源码级策略检查，不模拟 GitHub runner，不替代 YAML/Actions 执行验证或真实容器验证。此次不为测试而触发镜像构建或云端操作。

本决策只取代历史工作流中的自动镜像发布行为；历史部署记录保留，运行期媒体清理、内容理解、签名 FFmpeg 和目标环境验收要求不变。Draft PR 未合并前，主分支旧工作流仍存在，必须先合并本边界修复再批准其他 main 合并。
